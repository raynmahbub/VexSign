# VexSign streaming backup container

Updated 2026-11-08. Implementation: `BackupCrypto.sealFile/unsealFile` and
`BackupManager.makeBackup/open`. This is an implemented format, not an independently
audited security claim. Cryptographic review and Apple-device testing are release
gates. The version-3 JSON manifest is separate from this container's version.

## Scope and compatibility

New file backups use VEXBK3 and no longer allocate the entire ZIP for AES-GCM.
Encryption/decryption processes at most 1 MiB of plaintext per record, with a
per-record autorelease pool. Restore computes the ZIP's SHA-256 incrementally.
ZIP creation/extraction, library copies and JSON parsing still have their own
resource costs; temporary disk usage can be several times the source size.

The limits remain deliberate:

- At most 8 GiB expanded ZIP data and 50,000 ZIP entries, including directories.
- Library tree staging reserves one entry for its outer ZIP directory.
- At most 9 GiB of plaintext ZIP bytes and 9,216 nonempty records inside the stream container (plus the terminal record).
- At most 16 MiB of manifest JSON before decoding into memory.
- Legacy VEXBK0/1/2 file import is capped at 256 MiB of container bytes because
  those formats still require whole-buffer decryption. Oversized legacy files
  fail explicitly instead of attempting an unsafe allocation.

The earlier Data-based seal/unseal helpers remain for old formats and tests;
BackupManager no longer uses them for new files. Older app versions cannot read
VEXBK3. Passwordless files stay device-bound through the existing Keychain key;
use a password for migration. Backups containing certificates still require the
existing minimum-length password. Concurrent passwordless key creation is locked
to prevent one export from replacing another export's wrapping key.

## Exact framing

All integer fields below are unsigned big-endian. No platform-native integer
serialization is used.

The 84-byte envelope is:

| Field | Bytes | Meaning |
| --- | ---: | --- |
| Magic | 7 | UTF-8 `VEXBK3\n` |
| Wrap | 1 | 1 = password; 2 = device Keychain key |
| Salt | 16 | Random for password wrapping; zero for device wrapping |
| Wrapped key | 60 | AES-GCM combined box: 12-byte nonce, 32-byte encrypted content key, 16-byte tag |

The content key is fresh random AES-256 for each file. The password wrapping key
uses the existing PBKDF2-HMAC-SHA256 parameters: 200,000 rounds and a 32-byte result.
The wrapped-key box authenticates the first 24 envelope bytes as AAD. Its nonce is
randomly generated by CryptoKit.

Each following record is:

1. Four-byte plaintext length, from zero through 1,048,576.
2. Exactly that many bytes of ciphertext.
3. A 16-byte AES-GCM tag.

For record index `i`, starting at zero, the nonce is four zero bytes followed by
`i` encoded in eight bytes. This counter is unique under the fresh per-file key.
AAD is the complete 84-byte envelope, followed by the eight-byte record index,
followed by the four-byte length. No nonce bytes are stored with each record.

A zero-length record is the mandatory authenticated terminal record, using the
next unused index. Its tag must verify and the file must end immediately after
it. Thus dropping a suffix at a valid record boundary, appending data, substituting
another file's records, duplicating records or reordering records fails closed.
Empty input still emits the envelope and one terminal record.

## Publication, failure and cancellation

Both directions write a unique sibling scratch file with POSIX mode 0600. Every
record is checked for cancellation and size bounds. Decryption checks lengths
before allocating buffers; no decrypted ZIP is handed to extraction before the
terminal tag and EOF verify. Files are synchronized and closed before rename.
`moveItem` refuses to overwrite an existing destination. Ordinary failure removes
the scratch file and leaves existing files untouched. Abrupt process termination
can leave scratch files for OS/app temporary-directory cleanup; this is not a
crash-recovery journal or whole-library transaction.

BackupManager validates ZIP safety before sealing and before extracting. It
forwards cancellation into its detached sealing/opening workers and waits for
workers before deleting their work directories. Blocking ZIP/copy operations
remain cooperative at their operation boundaries. Per-app restore rollback and
preserve-existing behavior are unchanged.

## Validation status

`BackupStreamingTests` contains twelve Apple XCTest cases: multichunk and empty
round trips, wrong/missing passwords, envelope/ciphertext/length/tag corruption,
truncation, trailing bytes, swapped/duplicated records, preservation of existing
output, legacy decoding, oversized sparse legacy input, device wrapping,
cancellation, and an independent deterministic fixture.

The deterministic fixture uses password `streaming backup test password`, salt
bytes 0 through 15, content-key bytes 0 through 31, wrapping nonce bytes 16 through
27, and plaintext `VexSign streaming fixture\n` split after byte 13. It was generated
and decoded with Python cryptography's AESGCM plus hashlib PBKDF2, including
representative tampering checks. These fixed values are test-only; production
keys, salts and wrapping nonces are random. Swift fixture decoding, CryptoKit
execution, cross-device behavior, low-storage cleanup and large-library peak
memory measurements have **not** run on this Linux host.
