# VexSign threat model

This document describes the intended trust boundaries of the repository's current
implementation. It is not a security audit or a guarantee that every deployment
or device is secure. See [SECURITY.md](../SECURITY.md) to report vulnerabilities
privately.

## Scope and assets

VexSign imports arbitrary IPA/ZIP archives and can handle signing identities,
provisioning profiles, passwords, pairing files, repository feeds and optional
service credentials. The assets to protect are private keys and passwords,
account/session data, device data, local app files, and the integrity of signed
outputs and install links.

The primary adversaries considered are a malicious or malformed archive/feed,
a compromised or hostile network, an unintended reader of app data or logs, and
an incorrectly configured optional service. This model does not cover a
jailbroken or already-compromised OS, malicious Apple platform components,
physical access to an unlocked device, or the safety of apps from third-party
sources.

## Data handling and network boundaries

- **Signing identity and P12 password:** VexSign's certificate/secret utilities
  use the iOS Keychain for supported credentials and passwords. Signing reads
  identity material for the operation; do not export or share it in issue
  reports. Provisioning profiles and certificate-related records may also be
  imported and stored by the app for signing and management. Keychain protection
  depends on the device's security state and the app's access-control choices.
- **Local files:** IPA contents, downloaded files, and signing outputs are
  processed on device in the normal local-signing flow. Temporary workspaces are
  cleaned according to the app's operation/cleanup rules; this is not a promise
  of forensic erasure from flash storage or backups.
- **Local HTTPS installation:** the app creates a device-specific TLS identity
  for its local installation service and can provide the corresponding trust
  setup profile. This identity is for that local service; it is not a public
  web certificate. Users should install/trust only profiles generated by their
  own trusted device and remove them if no longer needed.
- **Repository and download traffic:** adding or refreshing a source, browsing
  release data, and downloading an IPA necessarily contacts the configured
  repository/hosting service. Those services can observe the request and normal
  network metadata. Repository data and downloaded archives are untrusted input.
- **Certificate status checks:** OCSP/CRL checks contact the relevant status
  responder when requested or when an enabled check runs. The responder may
  learn network metadata and certificate status query information. Network
  failures or unknown status must not be treated as proof of validity.
- **Optional cloud/backend features:** premium activation, recovery, catalog,
  account/provisioning experiments, cloud-signing bridges, and self-hosted
  backend operations may transmit data to the configured service. Review that
  service's deployment, privacy policy, logs, and retention before use. These
  features are separate from local IPA signing and may be incomplete or
  experimental.
- **Telemetry:** VexSign does not advertise a general-purpose analytics or
  advertising telemetry service. The app includes local activity analytics;
  that data is stored for display in the app. Network requests described above
  are feature traffic, not proof that no information can leave the device.
  Optional or user-configured network features have their own destinations and
  disclosures; users should review settings and service configuration.

## Main risks and mitigations

| Risk | Intended mitigation | Remaining limitation |
| --- | --- | --- |
| Malformed archive exploits extraction or exhausts resources | Validate archive entries and reject traversal, links and unsupported entries before extraction. | Parser vulnerabilities and resource-exhaustion cases remain possible; keep the app and OS updated. |
| Malicious IPA or tweak compromises the device/app | Signing and injection are explicit user actions; signing logs and output checks surface errors. | A correctly signed app is not necessarily safe. VexSign cannot sandbox every installed app or certify third-party code. |
| P12 password or private key leaks | Protected storage utilities, operation-scoped reads, and log redaction. | Device compromise, weak passcodes, backups, user exports, and implementation defects can expose material. Never share it. |
| Hostile repository or download | HTTPS-only repository transport by default, explicit local-HTTP opt-in, and untrusted-input handling. | HTTPS authenticates transport, not publisher intent or IPA safety; third-party feeds can change or disappear. |
| Local installation service is impersonated or misused | Device-specific TLS identity and local trust setup; authenticated Web Manager controls and explicit network access. | Local network exposure and trust-profile handling remain user/device responsibilities; TLS does not make a hostile IPA safe. |
| Logs/diagnostics disclose private data | Redaction filters and diagnostics guidance. | Redaction cannot be assumed perfect. Inspect exports before sharing and remove identifiers and tokens. |
| Optional server mishandles data | Optional features use configured endpoints; the backend and cloud signer are separate deployments. | VexSign cannot guarantee security, retention or availability of a third-party/self-hosted service. |

## User guidance

- Use a strong device passcode and keep iOS and VexSign current.
- Import signing material only from sources you trust; do not share `.p12`,
  private keys, passwords, profiles, pairing files, tokens, or unredacted
  diagnostics.
- Treat every IPA, tweak, source feed, URL and QR code as untrusted until you
  have independently assessed its publisher and contents.
- Enable optional network/cloud features only when you understand which endpoint
  receives the request. Self-hosting does not remove the need to secure that
  service.
- Report suspected vulnerabilities through GitHub's private reporting flow in
  [SECURITY.md](../SECURITY.md), not a public issue.
