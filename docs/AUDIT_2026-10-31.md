## 0. Executive summary

VexSign is **not** a thin Feather fork. It is a 64k-line application that already exceeds every
other project in this family in scope (Feather upstream is 11k lines), and much of the added
surface is real: archive-safety validation before extraction, HTTPS-only source policy with a
deliberate opt-in, Keychain-backed secrets with fail-closed migration, an offline repository
snapshot cache, source health/backoff, per-app update rules, an encrypted backup container,
a local HTTPS installer plus an idevice installation fallback, and a genuine test suite.

The weak points are not missing features. They are **correctness and trust boundaries around
the features that already exist**:

1. **Unenforced concurrency on the data path.** The two hottest write paths
   (import an IPA, sign an app) insert Core Data objects on a background thread through the
   main-queue `viewContext`. This is undefined behaviour per Apple and is the most plausible
   remaining crash/data-loss source. (§4.1, R1)
2. **The Web Manager can hand out signing identities to the LAN without authentication.** It
   is unauthenticated by default, binds `0.0.0.0`, and `/api/certs/:uuid/download` exports the
   p12, the profile and the p12 password in a plaintext `password.txt`. (§4.2, R2)
3. **Private keys are sent to third parties in two flows.** A remote "Apple status" checker
   POSTs the p12 *and its password*; a "NexCerts" catalog downloads third-party p12 +
   password and labels the entry "Official". (§4.3, R3/R4)
4. **Install success is guessed, not confirmed.** The installer polls
   `installProgressForBundleID:` and treats "progress went up, then to zero" as success.
   (§4.4, R5)
5. **Signing is fire-and-forget.** No output verification, no cancellation, coarse progress,
   and one provisioning profile for the whole bundle including its extensions. (§4.5, R6/07/08)
6. **The test suite never runs in CI.** 78 tests exist; no workflow executes them. (§4.9, R10)

Nothing in this audit recommends a rewrite. The signing pipeline, the storage schema, the
source pipeline and the installer are individually salvageable; what is missing is **one
verified path** through each of them, plus a CI gate that proves it.

## 3. Verified strengths (do not rewrite these)

### 3.1 Security work that is genuinely good

- **Archive validation before extraction.** `ArchiveSafetyValidator` rejects absolute paths,
  traversal components, NUL bytes, symlinks, >50,000 entries and >8 GiB expansion before the ZIP
  backend runs, and re-checks the normalised destination for containment
  (`VexSign/Utilities/ArchiveSafetyValidator.swift:44-97`). `.deb`/tar extraction applies the
  same rules in `Decompression.swift` (documented and tested by
  `StabilityAndArchitectureTests.testUnsafeArchiveEntryNamesAreRejected`).
- **Source transport policy.** `SourceURLPolicy` forces HTTPS for source add *and* refresh, with
  a clearly-labelled opt-in for LAN HTTP (`VexSign/Utilities/Security/SourceURLPolicy.swift`).
- **Secret storage.** Certificate passwords migrate into the Keychain with fail-closed behaviour
  and the Core Data `password` field is nulled afterwards (`CertificateSecrets`,
  `SecureSecretStore`); Web Manager password uses the same store
  (`WebManager.swift:27-30`, `55`).
- **Diagnostics redaction.** `DiagnosticBundleExporter` ships certificate metadata only, with a
  redaction pass covered by `EcosystemTests.testDiagnosticBundleSanitizerRedactsSecrets`.
- **Storage recovery instead of crashing.** `Storage._loadPersistentStoreAggressively()`
  (`Storage.swift:100-125`) resets a corrupt store, then falls back to an in-memory store rather
  than `fatalError`.

### 3.2 Reliability work that is genuinely good

- **Download resume + persistence** (`DownloadManager.saveResumeData`/`loadResumeData`,
  `DownloadManager.swift:372-390`, `654-700`), pause/resume/cancel-all, Wi-Fi/charging gates and
  a bounded parallel-download slot check.
- **Background keep-alive is refcounted** across signing, installing and the Web Manager
  (`BackgroundTaskManager`, with an `AVAudioSession` user count under an `NSLock`,
  `BackgroundTaskManager.swift:14-51`) — better than the single-owner silent-audio helpers found
  in Feather and its forks.
- **Continuation double-resume guard** in the import path
  (`AppFileHandler.swift:205-235`: `NSLock` + `didResume` + timeout), which is exactly the class
  of bug that produces "continuation already resumed" traps.
- **Offline source catalog + health/backoff + last-known-good retention**
  (`RepositorySnapshotCache`, `SourcePreferences`, `SourcesViewModel`).
- **Unified task ledger** (`UnifiedTaskCenter`) giving downloads/signs/installs one terminal-state
  model, with tests asserting terminal states are final.

### 3.3 Checked-and-correct (recorded so they are not "fixed" later)

- `ZsignHandler` passes `removeProvision: !_options.removeProvisioning`
  (`ZsignHandler.swift:59`). This looks inverted but is **correct for the pinned engine**: in
  `ZsignPackage/src/bundle.cpp:538-546`, the parameter named `excludeProvisioning` actually
  *writes* `embedded.mobileprovision` when true and removes it when false. The name is wrong, not
  the call. KorSign's neighbouring fork passes it un-negated and is the one that is wrong.
  **Consequence for R9:** upstream zsign renamed this to `-R/--rm_provision` with the opposite
  meaning; the call site must be re-derived from the new source, not copied.
- **R9 addendum (verified on both trees):** the `claration` `package` branch never fixed that
  polarity as such — it kept the write gated on the flag and *added* a delete of the same file
  during `CodeResources` generation for the same flag (`src/bundle.cpp:184-189` vs the write at
  `681-689`), so a bundle it signs ends up with no `embedded.mobileprovision` whichever way the
  flag is set. Upstream v1.1.3 has only the delete, and writes the profile unconditionally
  (`src/bundle.cpp:829-836`), which is why `-R` there means "sign, then strip the profile". The pin
  predates both and keeps the write-only behaviour the app relies on, so it stays.
- `VexSignApp`'s `BGTask` force-casts (`as!`) are gone; background task registration now uses
  guarded paths. The remaining `fatalError` is the unreachable `init(coder:)` stub in
  `DownloadOverlaySheetViewController`.
- The WebDAV handler resolves every request through `resolve(_:)`, which percent-decodes once,
  splits the path and rejects any `..` component before appending to the inbox
   (`WebManagerServer.swift:238-252`), and `DELETE` refuses the inbox root
   (`WebManagerServer+WebDAV.swift:72-77`), so the File-Manager-style exposure is limited to the
   inbox tree. The problem in §4.2 is authentication, not traversal.

### 4.1 F1 — Core Data written off the main thread (S0)

> **Status:** addressed by R1 (`docs/ROADMAP.md`); this section records the state at
> audit time. R1b added a main-queue tripwire on every view-context mutation, fixed one
> off-main insert (`FR.handleSource`) and turned on Core Data's concurrency assertion in the test
> action. The compiler-level gap — `@MainActor` on `context` and its read helpers — is R1c.

**What happens.** `Storage.shared.context` is `NSPersistentContainer.viewContext`, i.e. a
`.mainQueueConcurrencyType` context (`Storage.swift:40-42`). `addSigned` and `addImported` insert
directly into it (`let new = Signed(context: context)`,
`Storage+Signed.swift:29`; `Imported(context: context)`, `Storage+Imported.swift:27`), and
`nextSignedSortIndex()`/`nextImportedSortIndex()` then *fetch* from it.

Both methods are called from detached tasks:

- `FR.signPackageFile` runs in `Task.detached` (`FR.swift:64`) → `SigningHandler.modify()` →
  `addToDatabase()` → `Storage.shared.addSigned` (`SigningHandler.swift:205`).
- `FR.handlePackageFile` runs in `Task.detached` (`FR.swift:24`) → `AppFileHandler` →
  `Storage.shared.addImported` (`AppFileHandler.swift:223`).
- `AppCloner` reaches both from its own background work (`AppCloner.swift:120,132`).

`saveContext()` does hop to main (`Storage.swift:47-65`), which masks the problem in light use,
but the object graph has already been mutated and fetched off-main. The insert also constructs
`UIImpactFeedbackGenerator` on that thread (`Storage+Signed.swift:27`).

By contrast `addCertificate` is already `@MainActor` (`Storage+Certificate.swift:14`), which
shows the intended contract — it is just not applied consistently.

**Why S0.** Core Data documents main-queue contexts as main-thread-only. Violations produce
intermittent `NSInternalInconsistencyException`, object-graph corruption, or a save that silently
drops rows. This is the class of defect that survives a "stability hardening" pass because it
only appears under concurrent import/sign load.

**Direction.** Do not simply add `@MainActor` to the insert methods: imports and signs are long
operations and the UI should not block. Use `container.performBackgroundTask` (or a dedicated
`newBackgroundContext()`) for the write, return the `NSManagedObjectID`, and let the main context
merge (`automaticallyMergesChangesFromParent` is already enabled, `Storage.swift:35`). Keep the
`@MainActor` contract only for the UI-facing completion. Acceptance test: an XCTest that runs
N concurrent imports against an in-memory store and asserts N rows and no main-thread assertion.

### 4.2 F2 — Web Manager authentication and certificate export (S0)

> **Status:** addressed by R2 (`docs/ROADMAP.md`); this section records the state at audit
> time. `ServerInstaller+TLS.swift` still binds `0.0.0.0` and is tracked separately.

Verified chain:

1. `requireAuth` is read with `defaults.bool(forKey:)` → **false** when never set
   (`WebManager.swift:51`).
2. `WebManager.start()` only builds an `Auth` value when `requireAuth` is true
   (`WebManager.swift:75-77`); the middleware is therefore absent
   (`WebManagerServer.swift:145-150`).
3. The Vapor server binds `0.0.0.0` (`ServerInstaller+TLS.swift:46-48`) and the manager's URL is
   plain `http://<lan-ip>:8080/` (`WebManager.swift:128-130`).
4. `GET /api/certs/:uuid/download` zips the certificate and returns it
   (`WebManagerServer+HTTP.swift:169-176`). `CertificateExporter.makeZip` puts the p12, the
   `.mobileprovision` **and a plaintext `password.txt` with the p12 password** into that zip
   (`CertificateExporter.swift:13-40`).
5. `X-VexSign-Token` is checked **only** by `/api/sign` (`WebManagerServer+API.swift:154`,
   `257-265`), not by the certificate, file, WebDAV or import endpoints.
6. Body size is capped at **2 GB** for the whole server (`WebManagerServer.swift:231`), so an
   unauthenticated peer can also fill the device's storage.

**Exposure.** The server is user-started (a toggle in Settings → Web Manager), which limits blast
radius, but once started on a shared Wi-Fi the default configuration lets any peer list and
download the user's signing identity **including the password that unlocks it**, upload files
into the inbox, and POST new certificates. The UI does warn when running without auth
(`WebManagerView.swift:51`) — a warning is not a control.

**Direction.** Default `requireAuth` to true; require authentication *and* a token for
`/api/certs*`; make certificate export a separate, explicit permission; keep an unauthenticated
mode only behind a confirm dialog with a visible banner; consider a loopback-only bind mode for
users who only want Files-app/WebDAV access from the device.

### 4.3 F3 / F4 — Private keys leaving the device (S0 / S1)

> **Status:** F3 addressed by R3 (`docs/ROADMAP.md`) — the upload path is deleted, not
> gated. F4 addressed by R4 — the catalogue is contained, not removed (owner's call): it is
> labelled unofficial, the host is shown before any download, and the disclosure is acknowledged
> before the list is fetched.

- `CertificateStatusManager` posts a multipart body containing the p12 bytes and its password to
  `https://certchecker.novadev.vip/checkCert` (`CertificateStatusManager.swift:89`, body built at
  `:295-316`). There is a consent alert that names the operator
  (`CertificateDashboardView.swift:77`), so this is disclosed — but the on-device alternative
  already exists: `CertificateInspector` evaluates the certificate with
  `SecPolicyCreateRevocation(.OCSP)` and requires a positive response
  (`CertificateInspector.swift:65-80`). Sending the private key is therefore unnecessary for the
  feature's stated purpose.
- `NexCerts` downloads `cert.p12`, `cert.mobileprovision` **and the matching `password` file**
  from `https://sideloading.net/api/certificates` (`NexCerts.swift:14-60`) and imports them on a
  single tap. The entry point in Settings is labelled **"Official (NexCerts)"**
  (`CertificatesView.swift:121`), although these are third-party, shared, revocable identities
  with no pinning and no publisher verification.

**Direction.** Remove the remote p12 path (R3) and keep OCSP on-device. For NexCerts either
delete the feature or re-label it as an unofficial community catalog, show the source host and
expiry, require an explicit risk acknowledgement, and never auto-fetch a password without showing
where it came from (R4). This is also a ToS/compliance risk independent of the code.

> **What R4 did:** contained it. `OfficialCertificatesView` is now
> `CommunityCertificatesView`; "Official" appears nowhere in the UI or the string catalogue. A
> gate in front of the list names the host, states that the identity and its password are public,
> and that its owner can revoke it — and it must be passed before the catalogue is even fetched.
> Every import is confirmed individually, naming the certificate and the host. The stored
> acknowledgement is keyed by host, so a future host change re-asks instead of inheriting consent.
> See `docs/SECURITY_REVIEW.md` §9.

### 4.4 F5 — Install success is a heuristic (S1)

> **Status of F7:** addressed by R7 (`docs/ROADMAP.md`). `ProfileCompatibility`
> now compares the app with the profile before signing — coverage, extensions, entitlements,
> team, certificate and device — and blocks in preflight, which is where the user can still
> act on it.


> **Status of F6** (adjacent, and fixed alongside it): R6 adds
> `SignatureVerifier`, runs it on every produced bundle, logs the result, and
> blocks direct installs on its failures. The signed→install queue is not gated
> yet; see R6b in `docs/ROADMAP.md`.


`AppInstaller._startProgressPolling()` polls `UIApplication.installProgress(for:)` every 250 ms,
remaps `(raw - 0.6)/0.3` to UI progress, and when `hasStarted && raw == 0` sets
`status = .completed(.success(()))` (`AppInstaller.swift:372-380`). `SelfUpdateManager` uses the
same rule (`:342-357`). Consequences:

- A cancelled or failed install that decays to 0 is reported as success (and
  `AnalyticsStore.record(.appsInstalled)` fires, `AppInstaller.swift:322`).
- A slow install that momentarily reports 0 ends the UI early.
- There is no check that the installed version/build actually changed.
- The app cannot tell "installed" from "in library" anywhere else in the product.

KorSign (verified in source, GPL-3.0) demonstrates that a confirmation is possible in a jailed
app: `LSApplicationProxy.applicationProxyForIdentifier:` for `isInstalled`/`isPlaceholder`/
`shortVersionString`/`bundleVersion`, plus `LSApplicationWorkspace.installProgressForBundleID:`
phase/state and `ls_expectedFinalInstallPhase`, wrapped in an explicit state machine with
timeouts (`KorSign/.../InstalledAppProbe.swift`, `OTAInstallState.swift`). VexSign already uses
the same private selectors inside `NimbleKit`
(`UIApplication+open_private.swift:36-72`), so no new dependency is needed.

**Direction.** Implement `InstallConfirmation` as a pure, unit-testable state machine (phases,
deadline, evidence) plus a small `InstalledAppProbe` adapter; treat timeout as failure, never as
success; only record analytics on confirmed install. Reuse the same probe to display real
"installed" state in the Library (R5 + R16).

*Addressed by R5:* `InstallConfirmation` (waiting → downloading → verifying → verdict, with
120 s / 600 s / 20 s deadlines) and `InstalledAppProbe` (`LSApplicationProxy`, guarded, `nil` when
it cannot answer) replace the drop-to-zero heuristic in both `AppInstaller` and
`SelfUpdateManager`. An install is reported only when the device shows the app at the version that
was sent; a rolled-back install is reported as not installed, a dismissed prompt as cancelled, and
silence as a timeout with a retry — analytics fire only for proven installs.

*Addressed further by R16:* the same evidence now reaches the library. `LibraryStatusStore`
annotates every entry with what the device reports and with the certificate its stored signature
actually carries (`BundleSignature` → `SigningIdentity`), replacing `InstalledApps.isInstalled`,
which guessed from `canOpenURL` and was wrong in both directions. The library shows nothing rather
than claiming `.unknown`, hides "Open" for an app the device says is gone, and the expiry pill
counts down the bundle's certificate instead of the entity's row. Re-signing with a different
identity now warns before it happens, naming both certificates and the cost (no in-place update,
keychain data lost).

### 4.5 F6/07/08 — Signing correctness gaps (S1)

- **No verification of the result.** `SigningHandler.modify()` signs and then moves the bundle
  (`:151-180`). Nothing re-opens the signed binary, checks the code signature/CD hashes, confirms
  the embedded profile, or checks that the signed entitlements are a subset of the profile. The
  only verification in the product is `DirectInstaller.verify`, which checks a `_CodeSignature`
  directory and the presence of an LC_CODE_SIGNATURE — and is used only for "install as-is".
- **No profile compatibility check.** `PreflightChecks` covers bundle-ID sanity, missing
  Info.plist keys, certificate expiry, JIT-vs-PPQ and dylib architecture/duplicates
  (`PreflightChecks.swift:44-56`). It does **not** check:
  - explicit vs wildcard App ID against the target bundle ID (the most common install failure),
  - extension bundle IDs against the profile,
  - whether the app's entitlements (app groups, associated domains, iCloud, push) are all granted
    by the profile,
  - whether the signing certificate is actually present in the profile,
  - profile expiry (only certificate expiry is checked).
- **One profile for the whole bundle.** `ZsignHandler.sign()` passes a single `provisionPath`
  (`:53-66`) and the pinned engine signs every nested node with the same
  `ZSignAsset`. Upstream zsign now accepts repeated `-m` for per-extension profiles and `-P` to
  inject into extensions; the pinned 2025-07-27 engine does not. Apps with widgets/extensions and
  an explicit App ID therefore still depend on a wildcard profile.

**Direction.** Add `SignatureVerifier` (R6) used by both sign→install and sign→export, then a
`ProfileCompatibility` engine (R7) surfaced in preflight and in the certificate picker, then
the engine upgrade/nested-signing work (R8/R9). Order matters: the verifier gives the
engine upgrade a regression oracle.

### 4.6 F9 — Backup encryption (S1)

> **Status:** addressed by R11 (`docs/ROADMAP.md`). The plaintext container is no longer
> produced, certificate backups require a password, and old plaintext files still restore with
> a warning. This section records the state at audit time.

`BackupCrypto.seal` returns `plainMagic + plaintext` when the password is empty
(`BackupCrypto.swift:40-44`). `BackupManager.makeBackup` writes the p12 files and a manifest
entry containing `password: cert.signingPassword` (`BackupManager.swift:206-214`), and the UI
invites an empty password ("Leave it empty for an unencrypted backup.",
`BackupView.swift:67`). The security review already recommends otherwise; the code still allows
it.

**Direction.** If `.certificates` is selected, require a non-empty password (or always wrap with
a device-held key plus an optional user password). Add a restore-time integrity check and a unit
test asserting certificate-bearing backups are never plaintext.

### 4.7 F10 — Tests exist but never run (S1)

78 test methods across 7 files, all `@testable import VexSign`, all host-independent by design
(UserDefaults keys with unique names, file-scoped fixtures). The workflows compile the app
(`ci.yml` (build job)), the companions (`platform-check.yml`), the Python backend and the cloud
service — **none runs `xcodebuild test`**. The repository's own baseline document flags this as a
known gap (`docs/STABILIZATION_BASELINE.md` §1).

**Direction.** Add a macOS job that builds and runs the `VexSignTests` scheme on a simulator,
unsigned, with SPM caching. Treat it as required for PRs to `main`. That job is the gate every
other task in the roadmap depends on.

### 4.8 F11 — TLS private key material from the network at build time (S2)

`make deps` fetches `https://vexsign-install.vexsign.workers.dev/pack.json` with `curl` and
writes `deps/server.pem` and `deps/server.crt` from fields `key1`/`key2` (`Makefile:9,22-30`);
the app can also refresh the same pack at runtime (`FR.swift:190-200`,
`ServerView.swift:57`) and `ManifestService` uses the same worker for manifests
(`ManifestService.swift:14`). The installer then serves `itms-services` over TLS with that key
(`ServerInstaller+TLS.swift:74-91`).

The endpoints are HTTPS, but: the material is mutable and unversioned, there is no checksum or
signature, a compromised worker means every built IPA contains an operator-known key, and a
build without network silently produces an app with no bundled certificate. For a signing tool,
that is a supply-chain weak point worth closing.

**Direction.** Generate a deterministic self-signed certificate locally at build time (or ship a
documented development-only key with a clear warning), pin checksums for anything still
downloaded, and make the dependency explicit in the build output.

*Addressed by R12:* `make deps` now generates a development identity locally with `openssl` and
needs no network; the release identity is still downloaded but its digest is pinned in
`Scripts/local-tls/pinned-pack.sha256` and `make deps-release` (which the Release workflow runs)
refuses to build on a mismatch; the "build without a bundled certificate" fallback is gone. The
runtime refresh is a confirmed user action that validates the pack before writing it and shows
which identity is live. See `docs/RELEASING.md` § "Local install server TLS identity".

### 4.9 F12…F20 — Quality debt (S2/S3)

- **Cancellation (F12).** `FR.signPackageFile` is an unstructured `Task.detached` with a
  completion closure; no handle is returned, so the UI cannot cancel. `BatchJobRunner.cancel()`
  only sets a flag checked between items. Progress values are hard-coded (0.3, 0.8).
  *Addressed by R13:* runs are owned by `SigningService` and keyed by request, stages are
  reported as they happen (`.copying` … `.registering`), cancellation is checked between stages
  and mid-item in batch signing, and `clean()` guarantees a cancelled run leaves no bundle.
- **Concurrency mode (F13).** Swift 5 everywhere; `SWIFT_APPROACHABLE_CONCURRENCY` only on the
  widget. 27 `Task.detached` sites are invisible to the compiler.
- **Localisation (F14).** 2,110 distinct `.localized("…")` literals vs 1,428 catalog keys; 799
  used-but-not-in-catalog; 490 catalog keys have English only. Untranslated strings fall back to
  the key at runtime, so non-English users see English in exactly the newer feature areas.
- **Accessibility (F15).** 108 `.font(.system(size:))` fixed sizes, 24 `accessibilityLabel`,
  0 `accessibilityIdentifier`, 0 `dynamicTypeSize`, 5 reduce-motion checks. The app is usable but
  not audited; VoiceOver on the signing flow is untested.
- **Main-thread decode (F16).** `SourcesViewModel` decodes every repository JSON after the
  task group returns (`:270-300`) — for a large feed this is a visible hitch.
- **God files (F17).** See §2.2; combined with 54 singletons, unit-testing anything that
  touches signing/install state requires the whole app graph (R14).
- **Swallowed failures (F18).** 393 `try?`. Most are intentional cleanup calls; the risk is at
  boundaries (file replacement, plist writes, Keychain writes) where the user sees success.
- **DNS dependency (F19).** `NovaDNSDynamic` routes DoH through `dns.novadev.vip` and pulls
  rules from `api.novadev.vip`, used by the anti-revoke feature. It is opt-in and documented as
  not a guarantee, but it is a third-party observer inside a security feature (R22).
- **Integrity (F20).** Downloads record a SHA-256 in logs and offer a manual "Verify Hash…"
  flow, but source-declared `size` (present in `ASRepository`) is not enforced, and a mismatched
  hash never blocks import. A tampered download is only visible if the user looks (R21).

## 6. Architecture assessment

**What works.** The layering is conventional and mostly respected: `Views` → observable
managers (`Backend/Observable`) → handlers (`Utilities/Handlers`) → engine boundary (`ZsignHandler`,
`IDeviceSwift`, Vapor). Signing really is centralised: every re-sign path (auto-sign, batch,
update-all, self-update, IPA Explorer, SigningView) goes through `FR.signPackageFile`, and there is
one `ZsignHandler`. Downloads, sources and tasks each have one owner. That is why the roadmap can
be incremental instead of a rewrite.

**What does not scale.** (a) Reference-style singletons hold mutable state and are read from
detached tasks — the audit's S0 findings are all of this shape. (b) Views reach directly into
managers (`Storage.shared`, `DownloadManager.shared`), so nothing can be tested without the app.
(c) There is no value type describing "a signing request" — options, certificate, tweaks,
entitlements and paths are assembled ad hoc at ~7 call sites, which is why validation is
incomplete in every one of them. (d) Progress reporting is a set of ad hoc doubles rather than a
state machine.

**Target shape (incremental, no big-bang).**

```
SigningRequest (value: source app, cert, profile(s), options, tweaks, outputs)
      │
SigningService (actor; AsyncStream<SigningEvent>; cancellation; single pipeline)
      │── Preflight (pure)
      │── Modify (existing SigningHandler internals)
      │── Sign (ZsignHandler / engine)
      │── Verify (new: SignatureVerifier)
      └── Register (background Core Data context)
InstallService (actor; InstallConfirmation state machine; OTA and idevice strategies)
```

The same shape applies to imports and to backups. Each stage is pure enough to unit-test, and
each existing file survives — they become stage implementations rather than entry points.

## 8. Open questions / stop conditions

1. **Odysseus identity.** The brief's "Odysseus" resolves to `mirazbakis/Odysseus` (GPL-3.0,
   ★38, pushed 2026-10-07) — an advanced Feather + FreeSign fork with on-device Apple ID
   certificate provisioning and signed OCSP checks. If a different project was meant, say so;
   analysis of this one is in `REFERENCE_COMPARISON.md`.
2. **KorSign identity.** `korboybeats/KorSign` (★2, GPL-3.0, pushes 2026-10-13) is a RyukSign
   fork and is the only plausible match for "KorSign"/"KoSign". Recorded as low-confidence.
3. **NexCerts policy.** Removing it changes user-facing behaviour and may break a workflow the
   owner wants. The roadmap treats it as a *trust* fix (re-label + consent) by default, with
   removal as the recommended option.
4. **Widget deployment target (iOS 26) vs host (iOS 16).** Still unreviewed from the previous
   baseline; it needs a device pass before changing anything.
5. **Cloud signing.** There is no signer in `cloud-signing/`; the native client is a bridge only.
   The roadmap keeps it out of scope until a real signer and threat model exist.
