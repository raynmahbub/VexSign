## 1. Executive Summary

VexSign is a large, unusually defensive sideloading codebase, not a thin wrapper around one signing script. The current tree contains 1,448 Swift files (912 app, 228 unit-test, plus platform/service/package sources), local package graphs for Zsign, NativeSigning, SideSign, AltSourceKit, NimbleKit and IDeviceSwift, an on-device Swift WebManager, a Python WebManager service, a TypeScript cloud service, and host-integration packaging tools. Source paths for import validation, certificate storage, signing orchestration, post-sign verification, source parsing, downloads, backups, diagnostics redaction, notifications and account/session policy are real and mostly wired through view models, service adapters, persistence and task reporting.

The audit nonetheless rejects a "feature complete / release ready" conclusion. Three classes of gap dominate:

1. **No iOS build or runtime evidence exists here.** `xcodebuild`, `swiftc`, simulators, physical devices, real credentials and real IPAs were unavailable. `make verify` passed 90 portable gates, but those gates explicitly skip Swift syntax when `swiftc` is absent. `make typecheck` correctly failed with "needs xcodebuild". XCTest, XCUITest, native signing tests and package tests are prepared but were not run.
2. **A definite compile-breaking defect is present in the working tree.** `VexSign/Services/Injection/Planning/InjectionTargetAuthorization.swift:37` contains `for name where name.hasSuffix(".appex") {`; Swift requires `for name in names where ...`. The file is inside a folder-synchronized sources group, is referenced by `TweakHandler` and by a unit test, and therefore cannot be dismissed as unused. The green portable gate did not catch it because no Swift compiler ran locally.
3. **Several advertised or UI-visible capabilities are gated, external, or unverified.** Paired installation/removal is deliberately disabled by `InstallationAppProxy.hasAcceptedInventoryBridge == false`; computer-free bootstrap exists only as an iOS 27+ route with no device evidence; in-process Apple Account CMS signing is `.notIntegrated`; no verified paid-certificate provider or turnkey cloud signer is included; containers are VexSign-owned storage directories rather than isolated iOS app sandboxes; JIT and system location simulation are shown as unavailable; WebDAV `LOCK`/`UNLOCK` are stubs.

Hosted service validation is a genuine positive result: the Python WebManager suite passed **350 tests**, and the cloud TypeScript suite passed **41 tests with 2 skipped**, with `tsc --noEmit` and the OpenAPI contract check also passing. These results validate those hosted services and their fakes, not iOS signing, installation, device trust or Apple account behaviour.

The reference survey confirms that VexSign shares concrete architectural ancestry with Feather/RyukSign-family signers (import → modify → Zsign → archive → local install server), while adding stricter archive validation, bounded parsing, evidence-based installation confirmation, structured diagnostics, account/session policies and service surfaces. It is not a copy of any one reference. No source was copied during this audit; licenses and missing licenses are recorded in §4.

Readiness verdict: **not release-ready**. The tree needs a successful Xcode build after fixing F-050, hosted Swift test execution, a real-device acceptance pass, and closure or explicit product messaging for the gated/external capabilities listed in §15 and §16.

Post-audit remediation has since been applied for F-050, F-051, F-052, F-053, F-054, F-055, F-056, F-057 and F-058. The portable gates, hosted service suites and a compiler-free Swift loop check were rerun successfully; see §13. The Xcode build, XCTest/XCUITest and physical-device work remain outstanding.

## 17. Final Product Readiness Assessment

**Assessment: not ready for release or for a "complete implementation" claim.**

- The repository has coherent composition, explicit service boundaries, folder-synchronized target wiring and substantial defensive source code.
