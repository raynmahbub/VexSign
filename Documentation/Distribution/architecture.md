## Distribution feasibility matrix

| Method | Requirements | Device support | Limitations / current VexSign status |
| --- | --- | --- | --- |
| TestFlight | App Store Connect app record, eligible App Store Connect upload, Apple processing, beta configuration and tester access | Apple-supported iOS devices compatible with the app | Build upload and processing are separate from tester availability. No TestFlight upload exists in current workflow. Apple documents archive upload to App Store Connect for TestFlight [1][2]. |
| Ad Hoc | Paid Apple Developer Program team, registered device(s), matching Ad Hoc profile and distribution certificate | Only listed devices covered by the profile | Device caps and profile validity apply. Apple's Xcode guidance requires registered devices and a matching profile [1][2]. |
| Enterprise | Apple Developer Enterprise Program eligibility, organizational internal-use distribution, compliant certificate/profile and HTTPS hosting | Organization's eligible devices | Not public unrestricted distribution; membership is subject to Apple's requirements. |
| OTA | HTTPS manifest and payload plus an artifact signed for an eligible installation method | Compatible iOS versions and devices included/eligible for that signing method | OTA is delivery, not a signing class. A web `itms-services` link cannot turn an unsigned/App Store IPA or ordinary developer certificate into an installable public artifact. |
| MDM | Organization MDM service, managed/enrolled device and eligible app/license assignment | Managed devices | Organization infrastructure and enrollment required; not an independent public bootstrap route. |
| Personal Team | Personal Team signing/provisioning performed through supported Apple tooling and valid profile | Limited personal test devices | Apple documents up to 10 App IDs, 3 devices, up to 3 apps/device, with registrations/profiles expiring after 7 days [3]. VexSign's native flow is not integrated end to end, and account provisioning is not a public iOS API. |
| App Store / regional alternatives | Apple program and region-specific eligibility, notarization/review and platform rules | Only supported storefront/region/OS cases | Separate Apple entitlement/program requirements. Not implemented by this repository's release workflow. |

Sources (official Apple): [1] [Distributing your app to registered devices](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices.md), [2] [Distributing your app for beta testing and releases](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases.md), [3] [Apple Developer Program membership comparison](https://developer.apple.com/support/compare-memberships/), [4] [Apple device management overview](https://developer.apple.com/documentation/devicemanagement.md). Re-check current Apple documentation and account terms before each release; this table is a capability boundary, not a promise of eligibility.

## Implemented in this branch

The distribution foundation adds SwiftUI-independent models and validation in `App/iOS/VexSign/Distribution/Domain/DistributionModels.swift` and `App/iOS/VexSign/Distribution/Security/ReleaseManifestVerifier.swift`. It distinguishes release channels from distribution methods, rejects ineligible signing-class combinations, verifies an Ed25519-signed envelope before decoding its manifest, validates required fields/URLs/time/OS/bundle ID, and hashes artifact files in bounded chunks. Tests are in `App/Tests/VexSignTests/DistributionManifestTests.swift`.

`Tools/Release/sign-release-manifest.mjs` is a dependency-free Node.js signer for a detached Ed25519 envelope. It streams the IPA hash, validates signed metadata, signs canonical JSON bytes, and atomically publishes without overwriting an existing manifest. It reads the PKCS#8 private key only from `VEXSIGN_RELEASE_MANIFEST_PRIVATE_KEY`, never logs it, and requires a key ID from `VEXSIGN_RELEASE_MANIFEST_KEY_ID`. `Tools/Release/test-release-manifest.mjs` exercises signing, tampering preconditions, validation and output handling; the macOS CI build job runs it. **No production key has been generated/pinned and the release workflow does not invoke the signer.** Existing unsigned GitHub `RELEASE.json` / `BUILD.json` files remain provenance/checksum artifacts, not trusted signed manifests.

Unsigned CI/release IPAs can use `artifactDownload` + `unsigned` metadata for authenticated download and inspection only. That classification is explicitly rejected for direct OTA installation. A valid metadata signature never substitutes for Apple code signing.

## Planned component mapping (no duplicate implementations)

1. `App/iOS/VexSign/Distribution/Domain/` — manifest/release/channel/method/eligibility types (this phase).
2. `App/iOS/VexSign/Distribution/Security/` — signature and SHA validation (this phase); add archive bundle/profile inspection using existing `ArchiveSafetyValidator`, `CertificateReader`, and signature auditors.
3. `App/iOS/VexSign/Distribution/Infrastructure/` — release discovery wrapping existing `GitHubReleaseSource` / `SelfUpdateManager` fetch logic rather than another GitHub API client; resumable transfer wraps existing `DownloadManager` and recovery journal.
4. `App/iOS/VexSign/Distribution/Application/` — coordinator(s) reporting real state through `UnifiedTaskCenter` and using `InstallationCoordinator`/`AppInstaller`; no UI calls into Zsign directly.
5. `App/iOS/VexSign/Distribution/Platform/` — capability descriptions and supported handoffs around existing install/adaptor code; no private installer API.
6. Portal — mobile web experience may advertise only release channels whose signed package and eligibility checks pass. Existing GitHub release pages are the current host; static hosting deployment and iPhone-installable signed builds are not configured.
7. TestFlight — add a separate protected macOS workflow only after Apple distribution credentials, App Store Connect app record, archive signing/export and upload-state polling have been configured.
